Stemmer — The Complete Pipeline, Step by Step

Every stage from the PyTorch checkpoint through ONNX export, encoding, the transformer, decoding, and back out to audio files. Steps are numbered A1–H6 so nothing is skipped and any step can be referenced directly. Next steps and open questions are at the end.

The one-line map: PyTorch is used once, offline to produce a frozen .onnx file. At runtime, audio is fetched → decoded → chunked → STFT'd in NumPy → pushed through the ONNX graph (encode → transformer → decode) → ISTFT'd back in NumPy → overlap-added → written as stems.

Phase A — Build time (offline, once). PyTorch present.

Why tracing is required: Python is dynamic — loops, conditionals, dispatch — so you cannot statically read a flat op-list out of it. Running it once and recording what happened is the only reliable reduction. This is also exactly where the two export failures surfaced: torch.stft produces complex numbers (no ONNX data type), and data-dependent asserts branch on runtime values a static graph can't express. Both were moved outside the graph in A4.

Phase B — Runtime: request and ingest

Phase C — Preprocessing in NumPy (outside the ONNX graph)

Phase D — Inside the ONNX graph: encoding

Phase E — Inside the ONNX graph: the transformer (bottleneck)

Phase F — Inside the ONNX graph: decoding

Phase G — Postprocessing in NumPy, and output

Notice the symmetry: C4 turned complex into 4 real planes on the way in; G1 turns 4 real planes back into complex on the way out. C2's STFT is undone by G2's ISTFT. The ONNX graph sits exactly between those two mirrored pairs — which is the entire reason the split works.

The same pipeline, explained at three depths

For a 5th grader

Imagine a band playing in a room — a singer, a drummer, a bass player, a guitarist — and you record all of it with one microphone. Everything gets mixed together into a single sound, like fruit blended into a smoothie. Once it's blended, you can't just pick the strawberries back out. Our program un-blends the smoothie.

You give it a song — a file from your computer, or a link from YouTube or TikTok. The program goes and gets the song, then tidies it up so every song looks the same to it no matter where it came from. Then it hands the song to a kind of robot that has listened to millions of songs. Nobody ever told this robot what a singer sounds like; it practiced over and over, guessing and being corrected, until it got really good at hearing which sounds are the voice and which are the drums.

The robot is big and slow, so we don't give it the whole song at once. We cut the song into pieces about 8 seconds long, let the robot work on one piece at a time, then glue the pieces back together — carefully overlapping the edges so you can't hear where the cuts were. One more thing: the robot arrived in a giant heavy toolbox we didn't want to carry around, so we unpacked it and put just the important part into a small light box. Now it runs fast on a normal computer.

When it's done, the website shows a squiggly line for each part of the song. You can press play, turn the singer off to make karaoke, or download any piece. A five-minute song takes about 45 seconds.

For a high schooler

Sound is a wave — air pressure wiggling up and down — stored as 44,100 numbers per second per ear. There's a second way to look at it: turn it into a picture. Chop the audio into tiny overlapping slices and, for each slice, work out which pitches are present and how loud. Stack those slices and you get a spectrogram: time across, pitch up, brightness = loudness. A held note is a horizontal line; a drum hit is a vertical stripe.

That matters because neural networks are very good at finding patterns in pictures. The model we use (Demucs, from Meta) looks at both the picture and the raw wave, because they have opposite strengths — the picture tells you what instrument it is, the wave tells you exactly when things happen. A part called a transformer lets the two views compare notes. It learned by being shown millions of examples where the true separated tracks were known, and corrected every time it guessed wrong. Nobody wrote rules describing a voice.

The engineering problem: the model ships inside a huge research toolkit called PyTorch — great for scientists, far too heavy for a website. So we converted it to ONNX, a lightweight portable format. That failed at first, because the picture-making math uses complex numbers (a way of storing two facts about each pitch at once) and ONNX has no way to store those. The fix: cut the model in half — the picture-making stayed outside in ordinary code, and only the neural network core got converted. Then we checked both versions on the same song and confirmed they gave essentially identical answers.

The whole app: you submit a file or link → the server downloads and converts it to one standard format → checks whether it has already separated this exact song (if so, instant answer) → chops the audio into ~8-second chunks → each chunk becomes a picture → through the network → back into sound → glued together with overlapping edges → saved as audio files → and the website shows each part with its own waveform, play button and mute switch.

For a college student

Build time (once, offline). Demucs ships as two artifacts: a checkpoint (a state dict of ~40M float32 parameters) and the architecture as PyTorch nn.Module code. Neither is usable alone — the checkpoint has no topology, the code has no learned values. You instantiate the model, load the weights, then refactor to isolate the STFT/ISTFT at its boundaries, verifying the refactored forward pass reproduces the original at exactly 0.0 difference before touching the exporter.

Export proceeds by tracing: run one forward pass on a correctly-shaped dummy input; every tensor op is recorded and translated into the ONNX opset; Python control flow evaporates (loops unroll, conditionals collapse to whichever branch executed). Two things blocked a naive export — ONNX has no complex tensor dtype, so torch.stft had no translation, and data-dependent asserts cannot be expressed in a static graph. Both live only at the model's edges, because Demucs immediately converts its complex spectrogram to real/imaginary channels — the core is already real-valued. Hence the split. The result is a 166 MB self-describing graph, verified against the PyTorch oracle at max abs diff ≈ 2e-4 (≈ −74 dBFS), well under the LSB of 16-bit audio. Dynamic int8 quantization (166→56 MB) was implemented but shelved: measurable quality degradation on a transformer-heavy model, and no speedup on ARM since the int8 gains depend on x86 VNNI.

Runtime ingest. POST /jobs writes a SQLite job row and returns immediately. An asyncio pool capped at POOL_SIZE dispatches to an isolated subprocess (bounded peak RSS, hard timeout, killable, model loaded once per worker). URL ingestion runs yt-dlp sandboxed with host allow-listing and duration/size caps; ffmpeg normalizes to 44.1 kHz stereo float32. A content hash keys a dedup cache; the router then selects separators by mode and tier.

Preprocessing (NumPy). Chunk to ~7.8 s — the training segment length — with real surrounding context at boundaries rather than zero-padding (zero-padding presents an out-of-distribution discontinuity; this was a genuine bug caught by the oracle diff). STFT with n_fft=4096, hop=1024 (75% overlap), Hann window, center=True with reflect padding, one-sided → (2, 2049, T) complex → drop Nyquist → view_as_real → (4, 2048, T) real, where 4 = 2 stereo × {Re, Im}.

Encoder. Spectral branch: 2-D convolutions with kernels of shape (C_in, 3, 3), channels 48→96→192→384, strided downsampling; GELU between layers (without a nonlinearity, stacked affine maps collapse to a single affine map). Temporal branch: 1-D convolutions on the raw waveform, same channel progression. Skips retained at each resolution. Effective receptive field grows ~3→7→15→31 cells as the grid shrinks — trading spatial precision for semantic abstraction.

Bottleneck. A cross-domain transformer: learned Q/K/V projections, scaled dot-product attention (softmax(QKᵀ/√d)V), multi-head, with self-attention within each branch and cross-attention between them, fusing time-domain and frequency-domain representations. Placed post-downsampling because attention is quadratic in sequence length.

Decoder. Transposed convolutions upsample while channels contract 384→192→96→48, with encoder skips concatenated at matching resolutions — the U-Net pattern that restores the high-frequency spatial detail the bottleneck discarded. Outputs, per source: a spectral tensor (4 planes = 2 stereo × Re/Im) plus a direct temporal waveform. The graph terminates here.

Postprocessing (NumPy). Re-pair Re/Im into complex, ISTFT (inverse FFT per frame, window, overlap-add, normalize by summed window energy for NOLA compliance), sum the ISTFT'd spectral output with the temporal output per source, then overlap-add the chunk into the full-length buffer with cross-faded seams. Note the symmetry: C4↔G1 and C2↔G2 are exact inverses, and the ONNX graph sits precisely between those mirrored pairs.

Modes & serving. Music → Demucs. Video → Bandit (a band-split cinematic model: speech/music/effects). Full → chained, with Bandit's music bus recirculated through the entire Demucs path, yielding dialogue + sung vocals + instruments from a single clip. Stems are encoded as WAV (download) and MP3 (browser preview — full WAVs exhaust Web Audio memory), registered in SQLite, and a TTL sweeper purges source and stems. Measured throughput ≈ 0.15× real-time — a 4:55 track in ~44 s, CPU-only.

Next steps to implement

Detail and rationale for the first two live in StemSep_PRD_Addendum.md; the rest are carried over from the original PRD and from decisions deferred during Phases 1–5.

1. Instrument separation (the headline ask)

  • Quick win — htdemucs_6s: adds guitar and piano to the existing four stems. Nearly free: same architecture, same export path (A1–A10), same runner. Ship this first, and the oracle test verifies the new export automatically.
  • The right answer — Banquet (query-based): a stem-agnostic single-decoder model where you name the instrument you want. Comes from the same repo already integrated for Bandit, is only ~24.9M parameters (ideal for CPU), beats htdemucs_6s on guitar and piano, and reaches narrow classes like clean acoustic guitar, reeds and organ.
  • Instrument detection (PaSST): auto-detect which instruments a track contains so the UI can offer them, rather than making the user guess.
  • Stretch — AudioSep: free-text queries ("separate the solo violin"). Broader coverage, lower musical fidelity — an experimental mode, not the default.
  • Honest caveat: orchestral/symphonic separation is an open research problem — the field is still building datasets for it (SynthSOD, Spheres). Pop/rock instruments will work well; a dense symphony will be rough. Say this to Jack before investing heavily.

2. UI overhaul

  • Progress & timing (priority): live elapsed timer; a true progress bar during separation derived from chunks completed / total chunks (the chunk loop already knows the exact fraction — never ship a fake spinner); an ETA shown before work starts from the tier's measured real-time factor (~0.15× real-time → a 4:55 song ≈ 45 s); per-stage timings (download/decode/separate/encode); a final "took 44 s" summary; an explicit "returned instantly from cache" state; and weighted progress across both passes in chained Full mode. Requires the runner to report chunk completion back to the job row.
  • Transport: skip ±10s / ±30s, jump to start/end, click-to-seek, timeline ruler, current-time readout, keyboard shortcuts (space, arrows, M, S), playback speed 0.5–2×, A/B loop region.
  • Per-stem: colour-coded waveforms, volume + pan, live VU meters, waveform zoom + minimap, spectrogram toggle, collapse/reorder/rename.
  • Mixing & comparison: master volume, mute-all/reset, A/B against the original, save a mix preset, export a custom mix.
  • Workflow: recent jobs list, re-run same audio at a different mode/tier without re-uploading, job metadata panel, shareable result link.
  • Polish & performance: dark theme + design system, loading skeletons, server-side precomputed waveform peaks for long files, responsive layout, accessible transport controls.

3. Carried over / previously deferred

  • SDR eval harness — the biggest gap. Quality claims are currently qualitative. Needs ground-truth stems (a MUSDB18-HQ test track) to measure per-tier and per-model quality properly.
  • Revisit int8 quantization — currently shelved (quality loss on this transformer, no ARM speedup). Worth retrying with static or per-stem quantization once the eval harness can measure the damage numerically.
  • Stem-specific sub-models — a vocals-only export costs roughly ¼ of the full 4-stem bag. Big win when the user only wants one stem.
  • Reproducibility manifest per job — record model version, mode, tier, parameters, content hash and timings so any output is auditable and repeatable. (This is the provenance-receipt instinct applied here; see question 2.)
  • README + architecture doc — the repo still has uv's placeholder README. Write it before sharing the repo.
  • Push to GitHub — private first; confirm with Jack whether it belongs in a Cipher org.
  • Auto-mode detection — a light classifier ("is there speech here?") to pick Music vs Video mode automatically.
  • Deployment — Docker + a real queue (Redis/RQ) only if this needs to leave your machine; currently an in-process capped pool, no containers.
  • Bandit optimization — if it landed on the PyTorch fallback, export it to ONNX like Demucs so the whole production path is uniform.
  • Dynamic axes — currently sidestepped by fixed 7.8s chunks; revisit only if variable input shapes are ever needed.
